## A. 추정이 맞았던 것

### A-1. `TastePicker.tsx`가 사문화된 이유 — 확정

doc 10에 "지금의 스와이프 게임 이전 설계의 잔재로 추정"이라고 적었는데, **정확했습니다.**

PRD 2.3:
> **음식 선호도**: [ 면 vs 밥 ], [ 한식 vs 중식 vs 일식 vs 양식 ]

`TastePicker.tsx`의 주석과 정확히 대응합니다:
```ts
// 1. 단일 선택 (예: 면 vs 밥)
export function SingleSelect<T>...
// 2. 다중 선택 칩 (예: 한/중/일/양식, 주류)
export function MultiSelectChips<T>...
```

**PRD 원안을 그대로 구현한 컴포넌트**입니다. 이후 취향 수집이 카드 스와이프 게임(`음식 선호도 매칭 10문항`)으로 교체되면서 버려졌습니다.
→ 삭제해도 무방합니다. 다만 PRD의 `면 vs 밥`, `한/중/일/양식` 축은 현재 게임에 **없는 차원**이라, 되살릴지는 기획 판단입니다.

### A-2. `alcoholLiquor` canonical 이름 — 근거 확보

doc 10에서 "canonical 이름 결정 필요"라고 미뤄둔 문제에 원본 근거가 생겼습니다.

PRD 3.1 스키마:
```json
"alcohol_liquor": "Array[Enum(SOJU, BEER, COCKTAIL, WHISKEY, WINE, HIGH_ALCOHOL, MAKGEOLLI)]"
```

영상의 주종 7종과 **정확히 일치**합니다: 소주 / 맥주 / 칵테일·하이볼 / 위스키·양주 / 와인 / 고량주·전통주 / 막걸리

→ 원본은 **snake_case `alcohol_liquor`**. 현재 코드는 camelCase `alcoholLiquor`.
`personal_data`는 jsonb라 DB 제약은 없지만, 다른 필드(`bank_account`, `health_issues`, `preferred_location`)가 snake_case인 점을 보면 **snake_case가 원래 규칙**이었고 취향 게임 추가 시 camelCase가 섞인 것으로 보입니다.

### A-3. `Follow.role: 'leader'`의 정체 — 확정

doc 09에서 "`best`의 라벨이 `⭐ 친구`라 혼동 소지"라고 지적한 부분의 유래입니다.

PRD 3.1:
> **리더 메이트 (Leader Mate)**: 친구들의 일정 및 취향을 파악하여 약속을 주도하는 유저 역할

`leader`는 "친한 친구"가 아니라 **약속을 주도하는 역할**이었습니다. UI 라벨이 `친한 친구`/`⭐ 친구`로 바뀌면서 원래 의미가 사라졌습니다.

## B. 기획 의도와 구현이 어긋난 것

### B-1. 방 휘발성 정책 — 기준이 다름 ⚠️

PRD 2.2:
> 약속 일정이 **종료된 시점을 기준으로 24시간**이 지나면 해당 방은 자동으로 삭제(Destroy)됨

**현재 구현**: 방 **개설 시점**부터 24시간 (영상·실기기 모두 `23시간 59분 남음`으로 시작)

이건 의미가 완전히 다릅니다. PRD대로면 "약속이 끝난 뒤 정산할 시간"을 주는 정책인데, 현재는 "약속을 잡을 시간"이 24시간뿐입니다. **다음 주 약속을 잡으면 방이 먼저 사라집니다.**

영상에서 확정 후 카운트다운이 `28시간 20분`으로 늘어난 것은 약속 시각 기준 재계산의 흔적이라, **부분적으로만 반영된 상태**로 보입니다.

→ doc 04의 "개설 시 자동으로 약 24시간 부여"라는 제 기술은 구현 사실로는 맞지만, **기획 의도와 다르다는 점을 놓쳤습니다.**

### B-2. 이원화 캘린더 — 미구현 ⚠️

PRD 2.1의 첫 번째 핵심 기능입니다.
> **비공개 캘린더**: 개인 전체 일정 (타인 노출 불가)
> **공개 캘린더**: 친구에게 빈 시간 확인용으로 노출

**현재 코드에 이 분리가 없습니다.** `calendar_notes.visibility`(public/best/private)가 있지만 이건 **메모 단위 공개 범위**이지 캘린더 자체의 이원화가 아닙니다.

PRD의 "핵심 가치" 중 하나인 **프라이버시 보호 모델이 통째로 빠져 있습니다.**

### B-3. 공개 캘린더 4개월 제한 — 미구현

PRD 2.1:
> 당월 기준 총 4개월 치 데이터만 등록 및 노출 (예: 현재 6월일 경우 5, 6, 7, 8월만 활성화)

현재 `monthsList`는 **3개월 슬라이딩**입니다 (doc 06 참조). 개수도 다르고, "이전 1개월 + 당월 + 이후 2개월"이라는 구성 근거도 없습니다.

### B-4. 구글 캘린더 API → 기기 캘린더로 대체

PRD 2.1:
> **외부 연동**: 구글 캘린더 API 연동

**현재 구현**: `expo-calendar`로 **기기 시스템 캘린더** 연동 (삼성/Apple 캘린더)

기기 캘린더에 구글 계정이 연결돼 있으면 결과적으로 구글 일정이 들어오긴 하지만, **OAuth 기반 직접 연동이 아닙니다.** 웹에서는 동작하지 않고, 기기에 계정이 없으면 아무것도 안 옵니다.

doc 06에 "실제로 기기 일정을 읽어온다"고 검증했는데, 그게 PRD가 말한 연동은 아니라는 점을 함께 적어야 합니다.

### B-5. 성인 인증 — 미구현 ⚠️

PRD 3.2:
> **필수 정보**: 닉네임, 생년월일 (**성인 인증 및 카테고리 필터링용**)

PRD 3.3:
> **주류 카테고리 (성인 한정 활성화)**

**현재 생년월일은 수집만 하고 어디에도 쓰이지 않습니다.** 주종 선택 화면이 나이와 무관하게 활성화됩니다. 미성년자에게 주류 선택지를 노출하는 상태입니다.

실제로 제가 실기기 테스트에서 생년월일을 `20000101`로 넣었는데 아무 분기도 타지 않았습니다.

### B-6. 정산 알림의 전달 경로 — 절반만 구현

PRD 2.3:
> 정산 안내 메시지가 방 참여자들에게 자동으로 **푸시 알림 및 방 내 메시지**로 발송

**현재**: 푸시 알림만. `messages` 테이블에 시스템 메시지로 남기는 경로는 확인되지 않습니다.
(추방 시에는 시스템 메시지를 남기므로 패턴 자체는 존재합니다 — `App.tsx:2891`)

### B-7. 에브리타임 연동 — 흔적 없음

PRD 2.1:
> **에브리타임(에타) 연동**: 시간표 이미지 파싱 또는 URL 연동 기능 **검토**

"검토" 항목이라 미구현이 문제는 아니지만, 대학생 대상 서비스의 차별점으로 적혀 있던 항목입니다.

## C. PRD에 없는데 구현된 것

영상에서 본 기능 중 상당수가 **원본 기획서에 없습니다.** 개발 과정에서 추가된 것으로 보입니다.

| 기능 | PRD | 비고 |
|---|---|---|
| N빵 **상계(netting)** 로직 | ❌ | PRD는 단순 N분의 1만. 여러 건을 차감 정리하는 로직은 확장 |
| AI 영수증 OCR 정산 | ❌ | Gemini 기반 |
| 이모티콘 17종 (두두·모아·웰링·또리) | ❌ | 캐릭터 IP 4종 |
| 배달의민족 쿠폰 배너 | ❌ | Mock |
| AI 중간 약속 장소 / 소요 시간 | ❌ | 허브역 매칭 |
| AI 맞춤형 핫플레이스 + 광고 게이팅 | ❌ | 리워드 광고 모델 |
| 메뉴 룰렛 / 배민 설문 | ❌ | 도달 불가 화면 |
| 날씨 | △ | PRD에 "날씨 기반 부가 기능"으로만 한 줄 |

→ **PRD 대비 기능이 크게 늘었고, 그만큼 원래 핵심(이원화 캘린더·프라이버시)은 빠졌습니다.**

## D. PRD 자체의 공백

- **탭 2가 없습니다.** 문서에 "탭 1 : 캘린더", "탭 3 : 프로필"만 있고 탭 2 항목이 통째로 빠져 있습니다. 현재 앱은 2탭(일정 조율 / 채팅) + 설정 모달 구조라, 원래 3탭 설계였다가 축소된 것으로 보입니다.
- DB 설계가 `User` 엔티티 하나뿐입니다. Room / Participant / Message / DutchPay 스키마는 없습니다.
- `user_tag`가 `String(3 Digit, ex: '001')` — 현재 구현은 `100~999` 난수라 `'001'` 같은 값이 나올 수 없습니다. 형식이 다릅니다.

## E. 이 대조가 바꾸는 판단

| 항목 | 대조 전 | 대조 후 |
|---|---|---|
| `TastePicker` 삭제 여부 | "미사용이니 정리 대상" | **PRD 원안 구현체.** 삭제는 무방하나 `면 vs 밥` 축을 되살릴지는 기획 판단 |
| `alcoholLiquor` canonical | "ProfileSetup 이름을 표준으로" | **PRD는 `alcohol_liquor`(snake).** 다른 필드와도 일관 |
| 방 만료 24시간 | "정상 동작" | **기준이 잘못됨.** 약속 종료 후 24시간이어야 함 |
| `calendar_notes.visibility` | "메모 공개 범위" | 맞지만, **PRD의 이원화 캘린더와는 다른 개념.** 핵심 기능이 미구현 상태 |
| 생년월일 | "수집만 하고 미사용" | **성인 인증용이었음.** 주류 노출 제한이 빠진 것 |
| `Follow.role='leader'` | "친한 친구" | **"리더 메이트" = 약속 주도 역할.** UI 라벨이 의미를 지움 |

## F. 우선순위 제안

원본 기획 의도를 기준으로 다시 매기면, 지금까지 제가 정리한 이슈 목록과 우선순위가 달라집니다.

**기획 핵심인데 빠진 것 (신규)**
1. 이원화 캘린더 (비공개/공개 분리) — PRD 핵심 가치
2. 성인 인증 → 주류 카테고리 게이팅
3. 방 만료 기준을 "약속 종료 후 24시간"으로 수정

**기존 이슈 중 우선순위 상승**
4. 취향 데이터 저장 경로 연결 — PRD 3.3이 "약속 장소(메뉴) 선정 시 참고 데이터"라고 명시. 지금은 저장조차 안 되므로 **기획 의도가 완전히 실현되지 않은 상태**

**기존 이슈 중 우선순위 하락**
- `TastePicker` 미사용 — 의도된 폐기였음
- 앱 이름 3종 혼재(`@meety_`) — Meety가 원래 이름. 개명 흔적일 뿐
